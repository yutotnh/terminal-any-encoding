# AGENTS.md

terminal-any-encoding is a VS Code extension that lets you use non-UTF-8
encodings in the integrated terminal. It has two parts: the TypeScript core
(`src/`) and the transcoder (a luit fork, `transcoder/`). See
[CONTRIBUTING.md](CONTRIBUTING.md) for basic setup/test steps. This file only
covers the "this breaks if you're not careful" gotchas that are too specific
to put in CONTRIBUTING.md.

## Conversion tables and the luit fork

[CONTRIBUTING.md](CONTRIBUTING.md#repository-notes) covers the basics (no
formatter on `transcoder/`, regenerate tables instead of hand-editing). On
top of that:

- Every table comes from the `iconv-lite` devDependency, the library VS
  Code decodes and encodes files with, pinned to an exact version. Keep it
  at the version VS Code ships: a different one can make the terminal and
  the editor disagree. Its version is part of the generated
  `builtin_ja.c`, so a Dependabot bump fails `gen-tables-check` until you
  regenerate the tables and update the version in `THIRD-PARTY-NOTICES.md`.
- CI's `gen-tables-check` job runs `gen_tables.py --check` against
  `tools/gen-tables/golden/tables.sha256`, so a regenerated table without an
  updated hash fails CI.
- `tests/test_editor_parity.py` checks every byte sequence and every
  character of every encoding against iconv-lite. Its few intended
  differences (what typed ～, № and 〜 are sent as, C1 controls, GB18030's
  unassigned 4-byte ranges) are listed at its top; anything else that
  differs is a bug.
- Dependabot does not track luit's upstream (it's C code).
  `.github/workflows/upstream-watch.yml` checks weekly and files an issue.
  The fork's changes are the diff between `transcoder/vendor/luit-upstream/`
  and `transcoder/src/`; the reasons for them are in
  `docs/transcoder-design.md`.

## GitHub Actions dependencies

Workflows reference actions by exact tag (`@v4.4.0`), and
`.github/workflows/actions.lock` (generated by the
[`gh actions-lock`](https://github.com/github/gh-actions-lock) extension)
pins each one, including transitive ones, to a commit. GitHub enforces the
lock when a workflow starts: if a `uses:` doesn't match it, every workflow
in the repository fails with `startup_failure`. After changing any `uses:`,
run `gh actions-lock` and commit the lockfile with it. Dependabot's
github-actions PRs don't update the lockfile yet, so check out the PR
branch, run `gh actions-lock`, and push before merging.

## Node.js version

`.nvmrc` is the Node.js version for development/CI, which is different from
`engines.vscode` (the runtime Node.js inside the Extension Host). When
bumping it, keep `.nvmrc` and the `@types/node` major version in sync.

## Lower bound of engines.vscode

Don't decide the lower bound from the type definitions (`@types/vscode`)
alone. The extension relies on VS Code behavior that isn't part of the API
and can change without affecting compilation: shell integration is injected
because the transcoder is launched through a link named like the shell (VS
Code decides from the executable's basename), and a dismissed profile
QuickPick cancels VS Code's internal token. See
[docs/extension-design.md](docs/extension-design.md). When moving the lower
bound, verify against multiple real versions via CI's `integration-test` job
(the `vscode-version` matrix, or locally with
`npm run test:integration -- --vscode-version <version>`; see
[CONTRIBUTING.md](CONTRIBUTING.md#running-tests) for its prerequisites)
before settling on a value. The current lower bound is 1.73.0.

Lowering `engines.vscode` also lowers the runtime Node.js inside the
Extension Host (Node 16.14.2 for 1.73.0). `eslint-plugin-n` in
`.eslintrc.json` guards `src/**/*.ts` against this runtime floor (update the
version there too when you change the lower bound). However, it only looks at
global references and module members, so it can't catch misuse of prototype
methods like `Array#at` (`tsconfig.json`'s `"lib"` catches that separately).
It's a safety net, not a guarantee.
